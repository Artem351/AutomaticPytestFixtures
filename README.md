# AutomaticPytestFixtures

Плагин pytest для подготовки одного тестового стенда и последовательного запуска выбранной группы тестов по YAML.

Конфиг определяет компоненты, их порядок, параметры, привязки общих интерфейсов, тесты, тайм-ауты и восстановление после ошибок. Тесты используют обычные фикстуры pytest и не создают компоненты самостоятельно.

Встроенные компоненты моделируют питание, готовность системы и работу сервиса в памяти. Для примеров и проверок не нужны виртуальные машины, образы дисков и доступ к оборудованию.

## Установка и запуск

```console
python -m pip install -e .
python -m pytest
python -m pytest --stands-config examples/stand.yaml
python -m pytest --stands-config examples/overrides.yaml
```

- Обычный запуск проверяет сам плагин.
- `examples/stand.yaml` запускает тест изменения состояния и тест восстановления исходного состояния.
- `examples/overrides.yaml` запускает один параметризованный тест с разными реализациями интерфейса.

Плагин подключается через entry point `pytest11`. Без `--stands-config` он не создаёт стенд, интерфейсные фикстуры и каталоги артефактов.

Передавать расположение тестов отдельно не нужно: сбором управляет список `tests` из YAML, независимо от `testpaths` в настройках pytest. При заданном конфиге позиционные пути командной строки не определяют состав группы.

## Конфиг

Один файл описывает одну DUT и одну группу тестов:

```yaml
dut:
  type: mock

stages:
  - layer: hardware
    type: mock_power
    params:
      initial_on: true
  - layer: linux
    type: mock_linux
    params:
      file_name: image.qcow2
  - layer: linux
    type: mock_service
    params:
      name: web
      initial_running: true

bindings:
  power: mock_power
  system: mock_linux
  service: mock_service

tests:
  - examples/tests/test_basic.py::test_can_change_state
  - examples/tests/test_basic.py::test_initial_state_is_restored

timeouts:
  command: 30
  step: 300
  cleanup: 60
```

| Поле | Назначение |
| --- | --- |
| `dut.type` | Платформа; встроенные компоненты поддерживают `mock` |
| `stages` | Непустой упорядоченный список компонентов |
| `stages[].layer` | `hardware` или `linux` |
| `stages[].type` | Зарегистрированное уникальное имя компонента |
| `stages[].params` | Параметры, проверяемые моделью конкретного компонента |
| `stages[].timeouts` | Необязательные переопределения `command`, `step`, `cleanup` |
| `stages[].recovery` | Стратегия обработки ошибок компонента |
| `bindings` | Привязки интерфейсов для всей группы |
| `test_bindings` | Переопределения привязок для выбранных тестов |
| `tests` | Непустой список селекторов pytest в порядке выполнения |
| `timeouts` | Общие временные бюджеты |

Лишние поля, повторяющиеся ключи YAML, неизвестные компоненты и платформы, повтор компонента, неверные типы и несовместимые привязки отклоняются. Повтор одного типа компонента запрещён, чтобы экземпляры не перекрывали друг друга.

Компонент `mock_aux_power` представляет отдельный экземпляр питания и может использоваться вместе с `mock_power`.

### Пути и выбор тестов

Относительные пути в `tests` и `test_bindings` разрешаются относительно каталога конфигурации pytest (`pyproject.toml` или `pytest.ini`). Если такой файл не найден, используется каталог запуска. Расположение самого YAML не меняет базу путей: конфиг можно передать абсолютным путём из другого каталога.

Поддерживаются селекторы модуля, класса, функции и отдельного параметризованного случая:

```text
tests/test_device.py
tests/test_device.py::TestPower
tests/test_device.py::test_state
tests/test_device.py::test_state[main]
```

Селектор без конкретного параметра включает все его случаи в порядке сбора pytest. Повторно выбранный тест выполняется один раз. Модульный селектор включает все тесты модуля, поэтому для фиксированного состава группы перечисляйте функции или параметризованные случаи.

Плагин сохраняет порядок YAML и не переставляет компоненты ради удовлетворения зависимостей. `hardware` должен предшествовать `linux`; `mock_linux` требует ранее указанного `mock_power`, а `mock_service` — `mock_linux`.

Если дополнительные фильтры pytest исключили селектор из YAML, запуск завершается сообщением о ненайденном тесте. Группа рассчитана на обычный последовательный запуск; pytest-xdist не поддерживается.

## Общие интерфейсы и фикстуры

| Фикстура | Интерфейс | Методы |
| --- | --- | --- |
| `power` | `PowerControl` | `is_on()`, `set_on(on)` |
| `system` | `SystemInfo` | `is_ready()` |
| `service` | `ServiceControl` | `is_running()`, `start()`, `stop()` |

```python
def test_switch_off(power):
    assert power.is_on()
    power.set_on(False)
    assert not power.is_on()
```

Тест зависит от интерфейса, а не от `mock_power`, его параметров или реестра компонентов. Реализация всегда указывается явно, даже если доступен единственный вариант.

До подготовки стенда плагин проверяет зависимости выбранных тестов, включая интерфейсы, нужные их фикстурам. Привязка должна вести на компонент из `stages`, объявляющий и реализующий соответствующий интерфейс.

Необходимые интерфейсы следует объявлять в сигнатуре теста или его фикстуры. Динамический вызов `request.getfixturevalue()` не позволяет заранее обнаружить эту зависимость. При активном конфиге не перекрывайте имена интерфейсов локальными фикстурами.

### Привязки отдельных тестов

```yaml
bindings:
  power: mock_power

test_bindings:
  examples/tests/test_bindings.py::test_power_state[aux]:
    power: mock_aux_power
```

Сначала применяются привязки группы, затем подходящие переопределения от общего к более конкретному: модуль, класс или функция, отдельный параметризованный случай. Неуказанные интерфейсы сохраняют прежнюю привязку. Допускается указать привязку только для отдельного теста.

Неизвестный интерфейс, несовместимый компонент и селектор переопределения, не относящийся к выбранной группе, считаются ошибкой конфига.

## Жизненный цикл

1. YAML загружается и проверяется; строится план без создания компонентов.
2. pytest собирает выбранные тесты; проверяются нужные им привязки.
3. Перед первым тестом компоненты создаются и вызывается `setup()` в порядке YAML.
4. После каждого начатого теста вызывается `restore()` в обратном порядке, включая случаи падения и пропуска в теле теста.
5. После группы вызывается `cleanup()` в обратном порядке только для компонентов, подготовка которых была начата.

`restore()` возвращает изменённое тестом состояние к исходному, не повторяя подготовку всей системы. `cleanup()` окончательно освобождает ресурсы. Оба метода обязательны в контракте компонента.

Если подготовка упала, очищается и частично подготовленный компонент, и ранее начатые компоненты. Ошибка восстановления или очистки одного компонента не отменяет попытки обработать остальные. Ошибки сохраняются в журнале и не превращаются в успех.

После неуспешного `assert`, окончательной инфраструктурной ошибки или ошибки восстановления следующие тесты получают `skipped` с причиной остановки.

## Тайм-ауты и отмена

Все значения задаются в секундах. Допустимы дробные положительные конечные числа; строки, логические значения, ноль, отрицательные значения, `NaN` и бесконечности запрещены.

| Параметр | По умолчанию | Что ограничивает |
| --- | --- | --- |
| `command` | 30 | Одну попытку вызова подготовки, метода интерфейса или восстановления связи |
| `step` | 300 | Весь вызов подготовки или метода интерфейса вместе с повторами, `recover()` и задержками |
| `cleanup` | 60 | Один вызов `restore()` или `cleanup()` |
| `group` | `null` | Необязательный общий бюджет группы |

Компонент может переопределить первые три значения через `stages[].timeouts`. Неуказанное значение или `null` наследуется из общих настроек.

Сроки вычисляются по монотонным часам. Для операции выбирается наиболее ранний срок: попытки, этапа или группы. Восстановление состояния и окончательная очистка получают отдельный бюджет, даже если время группы исчерпано.

Методы выполняются в контролируемых daemon-потоках. При тайм-ауте контекст отменяется и вызывается `close()`. На совместное завершение метода и `close()` отводится дополнительно не более `min(0.25, cleanup)` секунды ожидания.

**Контракт отмены обязателен.** Компонент должен выполнять блокирующее ожидание через `self.context.wait()`, учитывать `self.context.remaining` при работе с I/O и закрывать сессию в быстром идемпотентном `close()`. Неблокирующие участки могут проверять `self.context.check()`.

Python не позволяет безопасно принудительно остановить произвольный поток. Если компонент игнорирует отмену или его `close()` зависает, runner признаётся непригодным и больше не вызывает его методы, включая `cleanup()`. Это инфраструктурная ошибка, а не успешная очистка. Другие компоненты продолжают очищаться.

Бюджет `group` проверяется до и после тестов и ограничивает вызовы компонентов. Произвольное тело Python-теста насильно не прерывается: бесконечный цикл вне интерфейсных вызовов не является прерываемой операцией компонента.

## Стратегии восстановления

По умолчанию действует `none`: одна попытка без восстановления. Встроенные mock-компоненты также поддерживают `retry`.

```yaml
stages:
  - layer: hardware
    type: mock_power
    params:
      fail_setup_attempts: 2
    recovery:
      strategy: retry
      attempts: 3
      delay: 0.01
```

`attempts` — общее количество попыток, включая первую. Между попытками вызывается реализованный компонентом `recover(error)`, затем выдерживается `delay`. Эти действия расходуют бюджет `step`.

Повторяются только явно восстанавливаемые `OperationError`. Исчерпание времени этапа или группы не запускает новый повтор. Неожиданные исключения не повторяются автоматически. `restore()` и `cleanup()` также не повторяются автоматически.

`none` не принимает `attempts`, отличный от единицы, и ненулевой `delay`: такие настройки не игнорируются молча.

### Управление mock-компонентами

Помимо предметных параметров доступны:

- `setup_delay`, `command_delay`, `restore_delay`, `cleanup_delay` — кооперативные задержки, по умолчанию нулевые;
- `fail_setup_attempts` — количество первых неуспешных попыток подготовки;
- `fail_restore`, `fail_cleanup` — моделирование соответствующих ошибок.

Эти параметры нужны для воспроизводимой проверки жизненного цикла, отмены и обработки сбоев. Они не запускают аппаратные операции.

## Ошибки, статусы и журнал

| Событие | Результат pytest |
| --- | --- |
| Неуспешный `assert` | `failed` |
| Типизированная инфраструктурная ошибка, в том числе внутри теста | `error` |
| Ошибка подготовки, восстановления или очистки | `error` |
| Тест после остановки группы | `skipped` |
| Обычный `pytest.skip()` | `skipped`, без остановки группы |
| Ожидаемое падение `xfail` | `xfailed`, без остановки группы |
| Нестрогий успешный `xfail` | `xpassed` |
| Строгий `XPASS` | `failed`, группа останавливается |

Метка `xfail` не скрывает типизированную инфраструктурную ошибку. Причины исходных исключений сохраняются через `__cause__`.

Основные ошибки находятся в `pytest_stands.errors`: `InfrastructureError`, `OperationError`, `OperationTimeout`, `StepTimeout`, `GroupTimeout`, `CleanupTimeout`, `RestoreError`, `CleanupError`, `RecoveryError`.

Успешный запуск возвращает стандартный код pytest `0`, неуспешный — `1`, ошибка конфига — `4`.

Каждый запуск с конфигом создаёт отдельный каталог внутри `artifacts/`:

- `config.applied.yaml` — проверенный конфиг с применёнными значениями по умолчанию;
- `run.log` — JSON Lines: по одному событию на строку.

Записи содержат `time` в ISO 8601 UTC с миллисекундами, `event` и поля события. Записываются подготовка, изменение и восстановление состояния, повторы, результаты тестов, очистка и завершение сессии. `passed`, `skipped`, `xfailed` и `xpassed` не смешиваются.

Другой каталог задаётся через `--stands-artifacts PATH`. Логи не удаляются после неуспешного прогона.

## Добавление компонентов

1. Описать параметры моделью-наследником `StageParams`.
2. Реализовать абстрактные методы нужного общего интерфейса.
3. Унаследоваться от `Stage`, указать `layer`, `platforms`, `provides`, `requires`, `params_model`.
4. Реализовать `setup()`, `restore()`, `cleanup()` и безопасную отмену в `close()`.
5. Для поддержки повторов объявить `retry` в `recovery_strategies` и реализовать `recover(error)`.
6. Зарегистрировать класс декоратором `register_stage("name")`.

Конструктор сохраняет параметры и зависимости, но не воздействует на DUT. Действия с ресурсами начинаются в `setup()`, чтобы runtime мог гарантированно учитывать начатые компоненты.

Новый интерфейс — абстрактный класс с методами, зарегистрированный через `register_interface("fixture_name")`. Компонент должен и унаследовать этот интерфейс, и перечислить его в `provides`.

Сторонний пакет может объявить функцию регистрации без аргументов:

```toml
[project.entry-points."pytest_stands.stages"]
my_components = "my_package:register_components"
```

Функция должна зарегистрировать интерфейсы и компоненты до построения плана. Примеры реализации находятся в `src/pytest_stands/layers/`.

## Структура и проверки

| Модуль | Ответственность |
| --- | --- |
| `config/` | Безопасная загрузка YAML и модели данных |
| `resolver.py` | Проверка контрактов и построение упорядоченного плана |
| `interfaces.py` | Общие интерфейсы |
| `layers/` | Реестр, базовые классы и mock-компоненты |
| `execution.py` | Контексты, отмена, тайм-ауты и восстановление |
| `errors.py` | Типизированные инфраструктурные ошибки |
| `plugin.py` | Сбор тестов, фикстуры, привязки, жизненный цикл и статусы pytest |
| `runlog.py` | Потокобезопасный журнал |
| `tests/` | Проверки границ конфигурации, исполнителя и запусков pytest в подпроцессах |

Проверки покрывают отказ до подготовки стенда, сбор по YAML, приоритет привязок, восстановление состояния, обратный порядок очистки, повторы и их исчерпание, отдельные временные бюджеты, отсутствие конкурентного повторного вызова после отмены, правильные статусы и отключённое поведение без конфига.
